## AI Agents Homework ##

Небольшой исследовательский проект, сравнивающий, насколько хорошо разные конфигурации LLM (по мощности модели и доступу к инструментам) отвечают на вопросы о недавних событиях, основанные на фактах, через API OpenRouter.

- **`tools.py`** — инструменты, которые может вызывать агент: `web_search` и `page_find` (Wikipedia), `ddg_search` (DuckDuckGo) для поиска фактов; `calculator` (безопасные арифметические выражения) и `python_exec` (код на Python в отдельном процессе с таймаутом) для вопросов с числами и датами.
- **`agent.py`** — цикл агента с вызовом инструментов: отвечает на вопрос, вызывая инструменты, пока не выдаст ответ `FINAL:` или не упрётся в лимит шагов; каждый запуск логируется в `traces/`.
- **`helpers.py`** — общие утилиты: запросы к OpenRouter с повторными попытками, учёт стоимости и токенов (`Ledger`), структурированные ответы без инструментов, загрузка датасета, проверка правильности ответов, сводка результатов и построение графиков.
- **`evaluation.py`** — прогоняет бенчмарк по нескольким конфигурациям (без tools / с подмножеством tools, дешёвая модель / сильная модель) на наборе вопросов и выдаёт точность, стоимость и скорость. Отдельно есть строка «wikipedia only» рядом с «search only» — сравнение дешёвой модели с одной только Википедией и с добавленным вторым источником (DuckDuckGo).
- **`main.py`** — точка входа, запускает оценку на `qa_data/fresh_2026.jsonl` - тестовый набор + новые вопросы и сохраняет сравнительный график (`money_chart.png`).
- **`test_tools.py`** — базовые тесты для инструментов.
- **`seminar/fetch_fresh.py`** / **`seminar/check_fresh.py`** — собирают и проверяют датасет вопросов о "свежих событиях" (фактах достаточно недавних, чтобы модель не могла ответить по памяти), который используется, чтобы оценить, действительно ли помогают инструменты.

### Установка ###

1. Создать и активировать виртуальное окружение:

   ```
   python -m venv .venv
   .venv\Scripts\activate      # Windows
   source .venv/bin/activate   # macOS / Linux
   ```

2. Установить зависимости:

   ```
   pip install -r requirements.txt
   ```

3. Создать файл `.env` в корне проекта (по образцу `.env.example`) и указать в нём свой ключ:

   ```
   OPENROUTER_API_KEY=your_key_here
   ```

4. Запустить оценку:

   ```
   python main.py
   ```

### Шаг 2. Индекс в Milvus и качество поиска ###

Две нарезки: наивная - по 400 символов без оглядки на границы и осмысленная - по строкам. Граница осмысленного куска проходит на переносе строки, потому что каждая обзорная страница устроена как список датированных событий, где одна строка, это одно законченное событие, а заголовок-месяц едет с ней как метаданные `section`. После нарезки - 6060 кусков по строкам и 2234 по 400 символам (порог задания в 300 кусков пройден с запасом).

Эмбеддинги (`openai/text-embedding-3-small`, 512 измерений) считаются один раз и кешируются на диск в `emb_cache.npz` (8.2 МБ, закоммичен) по sha1 текста - повторный прогон ноутбука ничего не пересчитывает. Обе нарезки проиндексированы в Milvus отдельными коллекциями (`lines`, `chars`) с метаданными `page`/`section`/`url`/`text` рядом с вектором. Демонстрация фильтра - поиск про землетрясения по коллекции `lines` с фильтром `page == "2026 in Japan"`, сужающим общую выдачу до одной страницы.

recall@k (по выдаче Milvus, k = 1, 3, 5, 10):

| k | по строкам | по 400 символов |
|---|---|---|
| 1 | 0.842 | 0.521 |
| 3 | 0.945 | 0.719 |
| 5 | 0.952 | 0.788 |
| 10 | 0.952 | 0.829 |

![recall@k](img/recall.png)

Recall@5 у нарезки по строкам (0.952) равен recall@10 (0.952) - рост k с 5 до 10 ничего не даёт, а нарезка по символам заметно хуже на любом k. Для шага 3 берём k=5 на нарезке по строкам: качество уже на плато, а контекст короче и дешевле, чем при k=10.

Гибрид (вектор / слова по IDF / RRF-слияние рангов), recall@1 и recall@5:

| нарезка | поиск | recall@1 | recall@5 |
|---|---|---|---|
| по 400 символов | только вектор | 0.52 | 0.79 |
| по 400 символов | только слова | 0.76 | 0.90 |
| по 400 символов | гибрид RRF | 0.70 | 0.90 |
| по строкам | только вектор | 0.86 | 0.98 |
| по строкам | только слова | 0.89 | 0.98 |
| по строкам | гибрид RRF | 0.88 | 1.00 |

Здесь гибрид не всегда выигрывает по recall@1 у одних лишь слов (0.70 против 0.76 на символьной нарезке, 0.88 против 0.89 на строчной) - вопросы в датасете короткие и обычно содержат редкое собственное имя или число, по которому точный поиск по словам уже почти не ошибается, а RRF слегка размывает верхушку списка вкладом вектора. Зато по recall@5 гибрид не хуже лучшего из двух источников, а на строчной нарезке даже выходит на 1.00 — там, где по отдельности ни вектор, ни слова полного покрытия не дают.

Потрачено на шаге 2: $0.0086 (эмбеддинги 6060 + 2234 + 146 + 10 текстов), в бюджет 30–50 центов на весь замер укладываемся с запасом.

### Вывод ###

Тезис курса подтвердился, причём с большим запасом: сильная модель без инструментов отвечает верно всего на 3% вопросов о 2026 годе, а дешёвая модель с двумя источниками поиска — на 59%, притом в 5 раз дешевле за задачу (0.00037 usd против 0.00191 usd) и в 19 раз дешевле за верный ответ. Даже самый слабый агент (только англоязычная Википедия, 25%) обгоняет сильную модель без инструментов по точности и всё равно дешевле её.

Неожиданностью было, что агент с Wikipedia + page_find (39%) оказался заметно хуже агента с Wikipedia + DuckDuckGo (59%), хотя `page_find` вообще не используется во втором варианте. Похоже, для такого датасета — недавние происшествия и события, разбросанные по многим разным статьям, — короткая выжимка из DuckDuckGo чаще прямо называет ответ, чем построчный поиск ключевых слов по длинной обзорной статье Википедии (см. первый разобранный провал выше: `page_find` находит нужный раздел, но не то, что внутри него). Второй источник поиска оказался полезнее чтения страниц — для этого конкретного датасета, не факт что это общий вывод.

Лучший результат дала средняя модель (claude-haiku-4.5) с полным набором инструментов — 67% при умеренной цене ($0.00745/задача). Это ожидаемо: более сильная модель лучше решает, когда каких инструментов достаточно и как интерпретировать найденное.
